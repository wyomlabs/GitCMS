TinaCMS is the most ambitious open source Git CMS around: schema in TypeScript, a GraphQL layer over your files, and click-to-edit on the live page. People look for TinaCMS alternatives when that ambition costs more than it returns. Usually that's TinaCloud's per-project bill multiplied across client sites, a frontend that now depends on Tina's data layer, or editors who can't change anything without a developer touching `tina/config.ts`.

The short map, by situation:

- **Keep the schema in TypeScript, drop the hosted GraphQL backend:** Keystatic.
- **Keep on-page visual editing on any static site generator, managed for you:** CloudCannon.
- **Spend nothing and keep it config-only:** Sveltia CMS or Decap CMS.
- **Non-developers need an admin with zero setup:** Pages CMS.
- **Hand the site to clients and AI agents, with review before publish:** GitCMS.
- **You actually want a content API:** a headless CMS.

## Why teams leave TinaCMS

Tina itself is healthy. It's Apache-2.0, developed by the Australian consultancy SSW, and ships constantly: `tinacms` 3.15.0 landed on October 19, 2026, and new CLI and GraphQL packages followed on October 27. Nobody leaves Tina because it's abandoned. They leave because of how it's built and billed.

### TinaCloud bills per project

TinaCloud is Tina's hosted backend: it handles sign-in and serves the content API. As of October 2026 the free plan covers two users. Team is $29 per project per month billed monthly ($290 a year), with three users included, a ceiling of ten, and $9 per extra user. Business is $299 per project per month with twenty users. Editorial workflow, Tina's branch-based drafting and review, starts at Team.

For one company site, that's reasonable. For an agency running fifteen client sites that each need review before publish, the "per project" part is the line item that starts the search.

### Self-hosting means running a backend

You can skip TinaCloud. Tina's self-hosting docs describe three modules you then own: an auth provider (Auth.js by default), a database adapter such as MongoDB or Postgres for indexing, and a Git provider that saves content. The docs also say some features aren't available when self-hosting. "Free and open source" is true, but you're now operating a database to edit Markdown files.

### Tina lives inside your codebase

Content models are defined in `tina/config.{ts,js,tsx}` with `defineConfig`, and content is queried through Tina's GraphQL Content API. That's a feature if your developers like typed queries. It also means adding a field, changing a collection, or swapping frameworks is code work, and your site's data fetching is tied to Tina's layer.

### Visual editing is React-first

Tina's contextual editing re-hydrates page data as you type, and its docs show that through the `useTina` React hook, with support for other frameworks such as Vue still in progress. If your site is Hugo, Jekyll, or mostly static Astro, the headline feature is harder to get.

### GitHub only, and AI is "coming soon"

Tina's FAQ says GitHub is the Git provider TinaCloud integrates with, and GitHub Enterprise support sits on the Enterprise plan. Its pricing page lists AI Assist as "coming soon" on every tier.

## When to stay on TinaCMS

Stay if your site is React or Next.js and click-to-edit on the real page is why your editors like the CMS. Few tools on this list do that as directly.

Stay if your developers use the GraphQL layer on purpose: references between documents, typed queries, generated clients. Replacing that with file reads is a real rewrite, not a config change.

And stay if the bill fits. One project on Team for a small team is cheaper than an engineer's afternoon each month. Leaving only pays off when the per-project cost or the backend work keeps adding up.

## TinaCMS alternatives, by situation

Pricing is as of October 2026. Check each vendor's current pricing before you commit.

### Schema in TypeScript, no hosted data layer: Keystatic

Keystatic is the closest in spirit for developers. Collections and singletons are defined in TypeScript, and the admin UI mounts inside your Astro, Next.js, or Remix app. The difference is underneath: no GraphQL server and no content database. Keystatic edits the files on disk or in GitHub, and your site reads them through a typed reader.

- **Best for:** developer-led sites that liked Tina's schema-as-code but not the infrastructure behind it.
- **Watch out for:** no on-page visual editing. In GitHub mode, every editor needs a GitHub account with write access. It's still 0.x, with the latest core release (0.6.9) in August 2026.
- **Pricing model:** free and MIT-licensed. Optional Keystatic Cloud handles sign-in and images: free for up to three users per team, Pro from $10 a month plus $5 per extra user.

See [GitCMS vs Keystatic](/compare/gitcms-vs-keystatic/).

### On-page visual editing on any SSG: CloudCannon

If visual editing is the part you'd miss, CloudCannon is the commercial option that isn't tied to React. It builds your site and can host it, and its visual editor works with Hugo, Jekyll, Eleventy, Astro, Next.js, and others. You mark up what's editable with Editable Regions or its Bookshop component system. It connects to GitHub, GitLab, and Bitbucket.

- **Best for:** teams where editors need to see the rendered page, especially on non-React static site generators.
- **Watch out for:** the visual editor needs a successful build on CloudCannon, so you're adopting its build pipeline too. It isn't open source and there's no free plan, only a 21-day trial.
- **Pricing model:** Standard is $55 a month billed monthly ($49 billed annually) with three users. Team is $350 a month. Extra users are $10 a month. Sites are unlimited on every plan, which is the opposite of Tina's per-project billing.

See [GitCMS vs CloudCannon](/compare/gitcms-vs-cloudcannon/) or our [CloudCannon alternatives](/alternatives/cloudcannon/) guide.

### Free and config-only: Sveltia CMS or Decap CMS

If what you want is the opposite of Tina, with no code in your site and no backend, the Decap family is a single-page admin that reads a YAML config file.

**Sveltia CMS** is the modern one: an MIT-licensed rewrite of Decap with a faster UI and strong i18n. It's still labeled beta (v0.253), and editors sign in with a GitHub, GitLab, or Gitea/Forgejo account with write access. **Decap CMS** is the original, now on a roughly monthly release cadence. It supports the widest set of Git backends, Bitbucket and Azure included, and in October 2026 it added Decap Turbo, a hosted backend where editors don't need Git accounts.

- **Best for:** developers who want a free admin and don't need visual editing.
- **Watch out for:** form-based editing, no live preview on your real site, and auth plumbing unless you pay for Turbo.
- **Pricing model:** both free and MIT-licensed. Decap Turbo has a free plan for one site and one seat; Pro is €19 a month.

See [GitCMS vs Sveltia CMS](/compare/gitcms-vs-sveltia-cms/) and [Decap CMS alternatives](/alternatives/decap-cms/).

### Non-developers, zero setup: Pages CMS

Pages CMS is a free, MIT-licensed admin for GitHub repositories. Add a `.pages.yml` file, sign in at the hosted app, invite collaborators by email. There's no build step, no SDK, and nothing in your frontend.

- **Best for:** small GitHub sites where the goal is "the client can fix a typo" and the budget is zero.
- **Watch out for:** GitHub only, no on-page editing, and no review or approval step described in its docs.
- **Pricing model:** free, hosted or self-hosted.

### Clients and agents, with review before publish: GitCMS

GitCMS is the CMS for code-first and AI-built websites. It gives your team, your clients, and AI agents one safe place to edit, review, and publish website changes, while everything stays in your site's repository.

The contrast with Tina is where the CMS lives. GitCMS adds nothing to your codebase except a `.gitcms/` config folder: no SDK, no GraphQL client, no change to how your site loads content. You connect an existing GitHub repository and your framework keeps reading files the way it already does. Editors get a document-style editor for Markdown and MDX, with frontmatter as form fields and MDX components kept intact (in beta). Changes move through content tasks, and with review before publish nothing merges until someone approves it. ChatGPT, Claude, and other MCP clients can draft inside those tasks too.

- **Best for:** agencies and freelancers handing Astro, Next.js, or AI-built sites to clients, where the editor and the review flow matter more than in-page editing.
- **Watch out for:** there's no click-on-the-page visual editing, so for a React site where that's the main requirement, Tina is better. GitHub only, like TinaCloud. It's a hosted paid product, not open source, and not a page builder.
- **Pricing model:** paid plans; you can connect a site and try it free. [See pricing](/#pricing).

See [GitCMS vs TinaCMS](/compare/gitcms-vs-tinacms/) for the head-to-head.

### You wanted a content API all along: a headless CMS

Some teams pick Tina for the GraphQL layer, then realize that what they want is structured content served to several apps. That's what headless CMSs are for. Sanity offers a free plan with up to 20 seats and Growth at $15 per seat per month. Payload is MIT-licensed and self-hosted. Either way, content moves out of your repository and into a database, which gives up the Git history and file portability that drew you to Tina. See [GitCMS vs Sanity](/compare/gitcms-vs-sanity/) and [GitCMS vs Payload](/compare/gitcms-vs-payload/).

## Migrating off TinaCMS

Your content is already Markdown, MDX, or JSON in your repository, so nothing has to be exported. The work is in your code, because Tina is part of it.

1. **Find every place the site queries Tina.** Pages that load content through Tina's generated client or GraphQL need to read files directly instead, for example through Astro content collections or your framework's own loaders. This is the biggest job, and a good one to hand to a coding agent with the list of files.
2. **Check your MDX.** If your editors used custom components inside Tina's rich text, those live in your MDX files. Any Git-backed editor you move to has to preserve them. GitCMS keeps MDX components intact (in beta), and it's worth testing a few of your most complex entries early.
3. **Remove Tina last.** Once nothing imports it, delete the `tina/` folder, the Tina packages, and any Tina commands in your build scripts, then cancel the TinaCloud project.

To move to GitCMS, connect the repository and run `npx create-gitcms@latest`, or ask Claude Code, Codex, or Cursor to run it. It scans your content folders and writes collections to `.gitcms/`. Your `tina/config.ts` is a useful checklist for the fields each collection should have. The [quick start](/docs/getting-started/quick-start/) covers the rest, and [the best CMS for AI-built websites](/blog/best-cms-for-ai-built-websites/) compares the wider field if your site came from a coding agent.
