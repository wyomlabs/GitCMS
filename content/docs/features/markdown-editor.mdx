GitCMS gives you a visual Markdown editor that feels closer to a modern doc tool than a raw text area, while still saving back to real files in your repository.

The goal is simple:

- writers and marketers should not need to think in raw Markdown syntax
- developers should still keep plain Markdown or MDX files in Git
- frontmatter should feel like a structured form, not YAML hand-editing

## What the editing experience feels like

When you open an entry in GitCMS, you work in a Notion-like editing surface:

- a visual body editor for the main content
- structured frontmatter fields above the document
- slash commands for inserting blocks quickly
- drag-and-drop block reordering
- media selection without leaving the editor
- internal link suggestions from your sitemap when available

## Body editing

The main document editor is built for everyday blog, docs, and changelog work.

You can insert and edit common blocks such as:

- headings
- bulleted, numbered, and to-do lists
- code blocks
- blockquotes
- callouts
- dividers
- tables
- images
- table of contents blocks
- equations

Use `/` to open slash commands and insert blocks without remembering Markdown syntax.

Blocks can also be moved with drag-and-drop, which makes it easier to restructure long content without cutting and pasting raw Markdown.

## Docs framework components

Docs frameworks add their own building blocks to Markdown: callouts, tabs, steps. GitCMS edits them as visual blocks, so writers don't touch the syntax. Content stays in your files in the framework's own syntax, and a block you didn't edit is saved byte-identical.

### Choose your framework

Open **Configure → Components** and pick one:

| Choice | Blocks |
| --- | --- |
| **Fumadocs** | Callout, Tabs, Steps, Cards, Accordions, File Tree and more |
| **Starlight** | Asides (`:::note`), Tabs, Steps, Cards, File Tree and more |
| **GitHub alerts** | `> [!NOTE]` style callouts, for GitHub-rendered docs, VitePress and Nextra |
| **None** | No docs components |

GitCMS detects the framework from your repository and marks it **Detected**. **Docusaurus** needs no choice: its admonitions and Tabs are built in.

### What you can edit

- **Callouts** (Fumadocs `<Callout>`, GitHub alerts, and `:::note` containers in Docusaurus and Starlight) open as a callout block with a type picker, an editable title, and a body. Changing the type renames it in the file, and an edited callout keeps the form it was written in.
- **Tabs** (Fumadocs, Starlight and Docusaurus `<Tabs>` / `<TabItem>`) open as visual tabs. You can rename, add, remove and reorder tabs. Renaming a Docusaurus tab keeps its `value`, so `defaultValue` and `groupId` still match.
- **Steps** (Fumadocs `<Steps>` and Starlight `<Steps>`) show a **Step** chip with **Add step below**, **Move up**, **Move down** and **Remove step**. Content you add after the last step stays inside a step.
- **Comments** (`<!-- -->`, or `{/* */}` in MDX) are shown as a Comment row you can edit. Text that would end the comment (`-->` or `*/`) is refused.
- **Imports** are shown read-only under the frontmatter. GitCMS adds the import a component needs when you insert it.

Type `/` and look under **Components** to insert one. The menu lists what your site has: the framework you chose, Docusaurus built-ins, and your [custom components](#custom-components). **Comment** is in the menu too. Components arrive as a valid empty block in the syntax the page already uses.

### Custom components

**Configure → Components** also lists the components your pages already use, with the fields GitCMS suggests from how each one is written: text, number, toggle, image or a choice of values. Owners and admins can open **Review** to adjust labels and types, then choose **Make editable**. The button is enabled once every page that uses the component still opens and saves unchanged.

A component written as code (`plans={…}`) stays as code and can be hidden from the list.

When an entry has a component GitCMS doesn't know, owners and admins also see **Make editable** under it in the editor. Writers see nothing new.

Each definition is saved in your repository at `.gitcms/sites/<site_key>/components/<Tag>.jsonc`. Edit it from **Configure → Components**, as with the rest of `.gitcms`.

### Docusaurus `.md` files

Docusaurus compiles `.md` files as MDX by default, so GitCMS does too. If your `docusaurus.config` sets `markdown: { format: 'detect' }` or `'md'`, GitCMS reads it automatically and opens `.md` files as plain Markdown. A page's own `format:` frontmatter (`mdx`, `md` or `detect`) takes precedence over the site setting. Heading anchors (`{#id}`), HTML comments and `:::` admonitions open visually on Docusaurus sites.

## HTML blocks and MDX

Use `/HTML block` to add a standalone HTML block to any entry. HTML blocks open with **Preview** and **Code** views: edit the markup in Code, then check it in Preview.

**In `.md` entries**, top-level raw HTML, such as a table or a `<div>` wrapper, opens as an HTML block. HTML mixed with text inside an ordinary paragraph stays part of that paragraph. Editing the paragraph can escape its tags, so use a standalone block for HTML you want to edit as source.

**In `.mdx` entries**, there is no raw HTML: tags are JSX. A block made only of HTML elements, text, and plain attributes (`class="…"`, `style="…"`, `colspan="2"`) opens as an HTML block. A block with expressions (`{…}`, `style={{ … }}`), components, or Markdown inside keeps the component source view. Either way, the source has to stay valid MDX for the entry to save.

The preview is a quick check, not your site. It shows the HTML without your site's styles, components, or scripts, and scripts in your content don't run. Tables get the editor's borders and padding in the preview only; nothing is added to the saved file. Tall content scrolls inside the preview. Edit HTML tables in Code: the controls for adding rows and columns work on Markdown tables.

### When an MDX entry opens as text

GitCMS never partially loads an `.mdx` file that isn't valid MDX. It opens the whole file as text, with a warning that names the line. Fix the error and save to return to the visual editor.

Agents connected through MCP get the same check. An agent can't save a change that would make a working `.mdx` entry invalid; GitCMS tells it the line to fix and saves nothing. An entry that is already invalid can still be edited, so it can be fixed in steps. If an AI edit in the editor leaves an entry invalid, it's shown as text: keep the edit and fix it there, or undo it.

In the visual editor, a change that would break the MDX, such as a component that lost its closing tag, isn't saved. GitCMS tells you which line to check. The usual fixes:

- Close void tags: `<br />`, `<img src="…" />`.
- Write comments as `{/* … */}`, not `<!-- … -->` (Docusaurus sites accept both).
- Close every component you open.
- Escape a literal `{` or `<` in text as `\{` or `&lt;`.

### What a save changes

Changing only an entry's fields leaves its body unchanged. When you edit the body, untouched blocks keep their original source formatting; edited Markdown blocks may be reformatted. When you change a field, GitCMS writes the frontmatter block again from its values: YAML comments are removed, and quoting and list style can change. The values themselves stay the same.

## Frontmatter without YAML editing

Above the document body, GitCMS renders your frontmatter as a structured editor instead of forcing you to edit raw YAML, TOML, or JSON by hand.

Depending on your collection schema, GitCMS can render frontmatter fields such as:

- title
- text
- rich text
- boolean
- number
- datetime
- select
- multiselect
- URL
- email
- slug
- image
- file
- groups and lists of fields (raw JSON until their fields are described)

That means fields like `title`, `description`, `publishDate`, `tags`, `author`, `featured`, or `coverImage` can be edited through purpose-built controls instead of plain frontmatter text.

For example:

- tags can behave like selectable chips
- image fields can open the media picker
- slug fields can be generated from patterns
- datetime fields can use date or date-time controls

For a full breakdown of schema and validation options, see [Collections & Fields](/docs/features/collections).

## Works with your frontmatter format

GitCMS preserves the frontmatter format your site already uses:

- YAML
- TOML
- JSON

You configure that at the site level, and the editor keeps working against that format. GitCMS does not force you to migrate your content model just to get a better editing experience.

## Media inside the editor

Image fields and body content can use GitCMS media workflows directly from the editor.

That means teams can:

- upload images into repository or object-storage media libraries
- pick existing media from the configured media libraries
- keep image references in Git-backed content files

See [Media Library](/docs/features/media-management) for media-specific behavior.

## Internal links without leaving the editor

If your site has a configured sitemap, GitCMS can help writers add internal links faster.

When you insert or edit a link, the editor can suggest published pages from your site so you can search instead of pasting URLs by hand.

This works especially well for:

- docs sites with lots of cross-links
- blogs that frequently link to older posts
- marketing sites with many landing pages

See [Sitemaps, Internal Links & Live URLs](/docs/features/sitemaps-internal-links) for setup and behavior.

## Draft recovery

GitCMS also helps protect in-progress writing in the browser.

If your editing session is interrupted, GitCMS can offer to restore your local draft the next time you open that entry. This is useful after:

- an accidental tab close
- a browser refresh
- a connection hiccup
- navigating away before saving

If the file changed in the meantime, GitCMS still lets you know that your saved draft may no longer match the latest version, so you can choose whether to restore it or continue from the current content.

## Custom SSG components in beta

GitCMS also includes beta support for editing custom SSG syntax inside Markdown and MDX content.

This is useful when your content includes framework-specific components or templating syntax that should be preserved instead of flattened into plain text.

Examples GitCMS can work with include:

- Hugo shortcodes like `{{< youtube id="..." >}}`
- Jekyll includes like `{% include component.html %}`
- Eleventy shortcodes
- JSX or MDX components used by Astro, Next.js, Gatsby, Docusaurus, and TanStack Start
- VuePress component syntax
- Nuxt MDC component syntax
- MkDocs or Jinja-style macros
- Svelte component syntax

<Callout type="info">
**Beta:** Custom SSG component editing works today, but it may still have rough edges while parsing or editing framework-specific syntax.
</Callout>

## Schema-aware, not generic

The editor is aware of your GitCMS site configuration.

That means it can use:

- your configured collections
- your frontmatter schema
- your file extension choice (`.md` or `.mdx`)
- your SSG framework
- your configured media libraries

If you have not defined a full frontmatter schema yet, GitCMS can also infer sensible field types from existing content and then let you refine the schema later in Settings.

## What stays true underneath

Even though the editor feels visual, the underlying model stays developer-friendly:

- content remains Markdown or MDX in your repo
- frontmatter remains plain frontmatter
- framework-specific syntax is preserved where possible
- Git remains the source of truth

GitCMS is not trying to replace your content files. It is trying to make those files much easier to work with.
