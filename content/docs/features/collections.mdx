Collections are the backbone of GitCMS. Each collection represents a type of content — blog posts, documentation pages, team members, product changelogs — with a defined set of fields that make up the frontmatter schema.

## What is a collection?

A collection maps to a directory in your repository. Every Markdown or MDX file in that directory becomes an entry in the collection. The frontmatter fields in each file are defined by the collection's frontmatter schema, and GitCMS renders a structured form for editing them.

```
src/content/blog/          ← collection "blog"
  ├── hello-world.mdx      ← entry
  ├── second-post.mdx      ← entry
  └── draft-ideas.mdx      ← entry
```

## Managing collections

Collections are configured through the **Settings** page in the GitCMS web app. You can add, edit, and remove collections and their fields entirely through the UI. The configuration is saved into your repository's `.gitcms/` folder. GitCMS manages that folder for you, so you don't need to edit it by hand; see [Configuration](/docs/getting-started/configuration).

### Collection settings

| Setting | Description |
|---------|-------------|
| **Name** | A unique slug for the collection (used in URLs and the sidebar) |
| **Label** | Display name in the sidebar. Defaults to a human-readable version of the name |
| **Description** | Optional help text describing the collection's purpose |
| **Content path** | The directory path for collection files (resolved in the site's config context) |
| **File extension** | `.md` or `.mdx` |
| **Filename pattern** | Template for new file names, built from field references and text tokens |

### Collection i18n paths

When site i18n is enabled, each collection can use locale-aware paths.

- Strategy is path-based (`path`).
- Default behavior uses locale folders (`/blog/fr/...`).
- You can set per-locale overrides when your framework uses custom folders.

Example override pattern:

```yaml
i18n:
  enabled: true
  locales: [en, fr]
  default_locale: en
  prefix_default_locale: false
collections:
  - name: blog
    git_path: /content/blog/
    i18n:
      enabled: true
      strategy: path
      locale_paths:
        fr: /content/fr/blog/
```

### Filename patterns

The filename pattern controls how new files are named when created through the CMS. You build patterns using the visual pattern builder in Settings, combining text and field references.

Examples:
- `{title}` — derives filename from the title field (e.g. `hello-world.mdx`)
- `{date.isoDate}-{slug}` — date prefix with slug (e.g. `2025-01-15-hello-world.md`), useful for Jekyll

Common patterns by use case:

- **Docs and marketing pages**: `{title}`
- **Blog posts**: `{date.isoDate}-{title}` or `{date.isoDate}-{slug}`
- **Changelog entries**: `{date.isoDate}-{title}`
- **Frameworks with stricter conventions**: match the filename pattern your site already expects

## Field types

Fields define the frontmatter schema for a collection. Each field has a name, type, and optional validation/display options. GitCMS supports the following field types.

The settings page shows each type by its label. In the configuration, the `type` is the lowercase value in the second column, and it's the value you'll see in error messages:

| In the editor | `type` in the configuration |
|---------------|-----------------------------|
| Title | `title` |
| Text | `text` |
| Rich Text | `richtext` |
| Boolean | `boolean` |
| Number | `number` |
| Date/Time | `datetime` |
| Select | `select` |
| Multi Select | `multiselect` |
| URL | `url` |
| Email | `email` |
| Slug | `slug` |
| Image | `image` |
| File | `file` |
| Group | `object` |
| List | `list` |

A group's type is `object`, not `group`. A `type` that isn't in this list stops the collection from loading, and the error names the file and field.

![Frontmatter fields rendered in the editor — title, description, date, image, authors, and tags](/images/docs/screenshots/fields-in-editor.webp)

### Title

A single-line text input optimized for entry titles. Typically used as the primary display field.

| Option | Description |
|--------|-------------|
| `maxLength` | Maximum character count |

### Text

A single-line text input for short text — slugs, author names, short descriptions.

| Option | Description |
|--------|-------------|
| `maxLength` | Maximum character count |
| `pattern` | Regex pattern for validation |

### Rich Text

A mini rich text editor for formatted text — descriptions, excerpts, bios. Uses a subset of the main editor's formatting capabilities.

| Option | Description |
|--------|-------------|
| `minLength` | Minimum character count |
| `maxLength` | Maximum character count |

### Boolean

A toggle switch for true/false values — draft status, featured flag.

| Option | Description |
|--------|-------------|
| `default` | Default value for new entries |

### Number

A numeric input with increment/decrement controls — sort order, priority, version numbers.

| Option | Description |
|--------|-------------|
| `integerOnly` | Restrict to whole numbers |
| `min` | Minimum allowed value |
| `max` | Maximum allowed value |
| `default` | Default value for new entries |

### Datetime

A date picker that outputs an ISO date string. Can optionally include time.

| Option | Description |
|--------|-------------|
| `withTime` | Enable time selection alongside date (date-only by default) |
| `timezoneMode` | `local` (default) or `utc` |

### Select

A dropdown menu for choosing a single value from predefined options — category, status.

| Option | Description |
|--------|-------------|
| `options` | List of allowed values |
| `allowCustom` | Allow other values than the listed options (**Allow other values** in Configure). On by default; `false` limits the field to the list |
| `color` | Notion-like tag color for visual distinction |

In frontmatter, the value is stored as a plain string.

### Multiselect

A tag-style input for choosing multiple values — tags, categories, labels.

| Option | Description |
|--------|-------------|
| `options` | List of suggested values |
| `allowCustom` | Allow other values than the listed options (**Allow other values** in Configure). On by default; `false` limits the field to the list |
| `color` | Notion-like tag color for visual distinction |

In frontmatter, values are stored as an array of strings:

```yaml
tags:
  - javascript
  - tutorial
  - react
```

### URL

A text input with URL validation. Use for external links, social profiles, canonical URLs.

### Email

A text input that checks for an email address. Use for contact and author emails. Fields with an email address, or named like `email`, are detected as email.

### Slug

A text field that GitCMS can generate from other fields when creating an entry, and that editors can override manually.
GitCMS preserves manually entered slugs exactly, including nested paths, trailing slashes, relative segments, capitalization, and Unicode. Your website's framework decides what each slug means for routing. Slugs must be text when present, and required slugs cannot be empty, but GitCMS does not impose a universal URL format.

When generating a **filename** from a slug (via the collection's filename pattern), the result must still be a safe relative repository path. A frontmatter slug like `../guide` is accepted as content, but cannot be used to create a file outside the collection.

| Option | Description |
|--------|-------------|
| `pattern` | Pattern referencing other fields (e.g. `#{title}-#{date}`) |
| `autoGenerate` | Whether the slug is auto-generated from the pattern |

By default, the slug can stay in sync with the generated value as you update the fields that feed it. If you manually edit the slug, GitCMS keeps that custom value instead of forcing it to regenerate on every change.

### Image

An image picker that integrates with the media library. Users can upload a new image or select an existing one.

The stored value is the file path relative to the repository root.

### File

A file picker for downloads and other non-image files: a PDF, a GPX route, a spreadsheet. It opens the [media library](/docs/features/media-management) filtered to the file types you allow, and users can upload a new file or choose an existing one.

| Option | Description |
|--------|-------------|
| `extensions` | Allowed file extensions, such as `["gpx", "kml"]`. Leave it out to allow any file |

```json
{ "name": "route", "type": "file", "extensions": ["gpx"] }
```

Extensions are case-insensitive. Type them with or without the leading dot (`GPX`, `.gpx`, and `gpx` are the same); GitCMS stores them lowercase without the dot. In settings, enter them in **Allowed extensions**, separated by commas.

The stored value is the file's path in the format set by [Links](/docs/features/media-management#links), such as `/files/route.gpx`:

```yaml
route: /files/route.gpx
```

The picker only accepts uploads with an allowed extension, and the editor flags a path that has a different one. A field holds one file. For several, use a [List](#list) whose items contain a File field:

```json
{
  "name": "routes",
  "type": "list",
  "fields": [{ "name": "track", "type": "file", "extensions": ["gpx"] }]
}
```

```yaml
routes:
  - track: /files/morning-loop.gpx
  - track: /files/ridge-trail.gpx
```

AI agents see a file field as a string path, with the allowed extensions in its description.

### Group

Related fields kept together under one key, like an `seo` object with a title and description. List the fields inside it; groups can hold lists and other groups. In the configuration, a group's `type` is `object`.

```yaml
seo:
  title: Pricing that scales
  description: Simple plans for every team
```

A group without fields is edited as raw JSON. In the site settings, **Describe fields from content** fills in its fields from a sample entry.

Configs from before v1.4 had a separate JSON field type; upgrading turns each one into a group, with its fields described from a sample entry when there is one.

### List

Repeated items, each with the same fields: authors, links, FAQ entries. In the configuration, the `type` is `list`. Editors add, duplicate, reorder, and remove items without touching the file's syntax.

| Option | Description |
|--------|-------------|
| `fields` | The fields of each item |
| `itemLabel` | How each item is named in the editor, using its fields in braces, e.g. `{name} · {role}`. Defaults to the item's first title or text field |

```yaml
links:
  - label: Docs
    href: /docs
  - label: Blog
    href: /blog
```

A list without fields is edited as raw JSON, and can be described from content the same way. For a list of plain words, use **Multiselect**.

## Common field options

Every field type accepts these shared options:

| Option | Description |
|--------|-------------|
| **Name** | The frontmatter key (required) |
| **Type** | The field type (required) |
| **Label** | Display label in the editor — auto-derived from the name if not set (e.g. `publishDate` becomes "Publish Date") |
| **Description** | Help text shown below the input |
| **Required** | Whether the field must have a value |

## Files that aren't content

Setup doesn't make collections out of files that are about the repository: `README`, `CHANGELOG`, `CONTRIBUTING`, `LICENSE`, `SECURITY`, and `CODE_OF_CONDUCT` files, agent instructions such as `AGENTS.md` and `CLAUDE.md`, and anything in a `vendor`, `third_party`, or `bower_components` folder.

A folder named `build` is left out only when `.gitignore` lists it or its files have no front matter, so a docs section about building stays.

This applies to what setup suggests. A collection lists every file of its type in its folder.

## How folders become collections

In a content folder such as `content/`, each folder inside it is its own collection. When more pages sit directly in the folder than in any one folder inside it, as in a docs site, the whole folder is one collection instead.

Because a collection takes every file in its folder, pages beside collection folders (such as `content/about.md` next to `content/blog/`) or at the site root can't be in one. Setup counts them and says where they are.

## Schema inference

If you don't define a frontmatter schema for a collection, GitCMS automatically infers field types from your existing content. It analyzes the frontmatter in your Markdown files and detects:

- Common field names like `title`, `date`, `description`, `image`, `tags` are mapped to appropriate types.
- Values that look like dates become datetime fields.
- Values that look like URLs become url fields.
- Arrays of strings become multiselect fields.
- Objects become groups, and lists of objects become lists, with their fields detected from every item.
- Boolean values become boolean fields.

During setup, GitCMS reads up to five entries of each collection, so a field that only some entries use is included, and a field with different kinds of values gets one that fits them all.

This means you can start using GitCMS immediately without defining any schema — it just works with your existing content. You can then refine the schema through Settings for better labels, validation, and field-specific options.

In practice, this is useful when:

- you are bringing an existing content site into GitCMS
- your frontmatter is already consistent enough to recognize common patterns
- you want a fast first pass before fine-tuning field labels and validation

## Multiple collections

Most sites have more than one type of content. Add as many collections as you need through the Settings UI. Each collection appears as a separate entry in the sidebar with its own listing page.

Common patterns:

- **Blog posts** — `src/content/blog` with title, date, tags, draft status
- **Documentation** — `content/docs` with title, order, section
- **Changelog** — `content/changelog` with title, version, date
- **Team members** — `content/authors` with name, bio, avatar, social links

## Tips

- **Keep field names consistent with your framework.** If your Astro config expects `pubDate`, name the field `pubDate` in your frontmatter schema — not `date`.
- **Entries must fit their fields to save.** A required field left empty, a slug with spaces, or a value outside a field's options stops the save, in the editor and through AI agents alike. The field shows what's wrong, and **Save** points you to it.
- **Use required sparingly.** Only mark fields as required if your build will break without them. Optional fields with sensible defaults reduce friction for content creators.
- **Use descriptions liberally.** Brief help text prevents confusion, especially for non-technical team members.
- **Start simple.** You can always add more fields later. GitCMS infers schema from existing content, so you only need to define fields when you want specific types or validation.
