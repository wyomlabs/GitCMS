---
title: Localization (i18n)
description: Configure multilingual content in GitCMS with locale-aware collection paths, default locale behavior, and per-locale overrides.
---

GitCMS supports locale-aware content workflows for multilingual sites.

You can:

- define site locales (for example `en`, `fr`, `de`)
- choose a default locale
- control whether the default locale is prefixed in paths
- configure per-collection locale path overrides

## Languages in Configure

Open the site's **Configure** → **Languages**:

- **Languages** lists the site's languages by name and code (for example "Français fr"). Use **Add language** to add one, **Make default** to change the default, and remove a language from its row. A site is multilingual once it has two languages; there is no separate switch.
- **Translated collections** is a table with a collection per row and a language per column. Turn a collection on to translate it; each cell is the folder that language's entries live in (`locale_paths`), and the default language shows the collection's own folder. Adding a language fills in folders for translated collections, following where their other translations live. Collections you don't translate are listed under **Not translated**.
- **Website URLs** chooses whether the default language's addresses carry its code, shown with real examples from your site (for example `/blog/hello` or `/en/blog/hello`). Other languages always carry theirs (`/fr/blog/hello`).

## Default language in addresses

Assume collection path is `/posts/`, default language is `en`, and the other is `fr`.

| Website URLs | `en` path | `fr` path |
|--------|-----------|-----------|
| Without the code | `/posts/hello-world` | `/posts/fr/hello-world` |
| With the code | `/posts/en/hello-world` | `/posts/fr/hello-world` |

## In the configuration

Translation is path-based (`strategy: path`). `locale_paths` overrides where a language's entries live, for framework-specific folder structures.

Example:

```yaml
i18n:
  enabled: true
  locales:
    - en
    - fr
  default_locale: en
  prefix_default_locale: false
collections:
  - name: docs
    git_path: /content/docs/
    i18n:
      enabled: true
      strategy: path
      locale_paths:
        fr: /content/fr/docs/
```

## Editor behavior

- Web app locale switcher keeps you in the same context (entry, history panel, or collection) while switching locale.
- New-entry drafts are locale-scoped, so drafts for `en` and `fr` do not collide.
- Production link and collection listing respect the selected locale context.

## MCP and AI behavior

GitCMS MCP tools are locale-aware.

For multilingual workflows, explicitly mention target locale in your prompt (for example: "use locale `fr`"). This helps AI read and write the intended locale path.

## Translations by file name

GitCMS groups translations kept in a folder per language, such as `content/es/`. It can't yet group translations named by language, such as Hugo's `post.es.md`: each file is listed as its own entry. Setup says how many it found.

## Detection during onboarding

Setup, in the web app and the CLI, sets up i18n for you.

**Your framework's language config comes first.** When a site declares its languages, those are the site's languages and its default, and only folders named after them are treated as translations. GitCMS reads:

- Hugo `languages` in `hugo` or `config` files, including `config/_default/languages.*`
- Astro `i18n`, or Starlight `locales`
- Next.js `i18n` in `next.config` or `next-i18next.config`
- Nuxt `i18n`

A declared language with a region, such as `en-US`, uses the `en-us/` folder, or `en/` when it's the only declared language that could. Your site's locale codes then match the folder names.

**Hugo's default language has no prefix** unless `defaultContentLanguageInSubdir` is on, even when its pages are in `content/en/`. Setup follows that: **Default locale path** stays off, and each collection's `locale_paths` points the default language at its folder:

```yaml
i18n:
  enabled: true
  strategy: path
  locale_paths:
    en: /content/en/
```

**Otherwise GitCMS reads the folders.** Only real language codes, such as `fr` or `pt-br`, count.

- **All language folders.** When a collection holds two or more language folders and nothing else, such as `content/en/` and `content/fr/`, each is a language, even if the page names are translated.
- **Beside other content.** A language folder next to other pages or folders counts only when its pages mirror them: at least half exist at the same path among the untranslated pages, or it shares at least half the pages of the smaller of the two with another language folder.

So a folder like `it/` holding IT service pages beside your other posts stays an ordinary folder.

Untranslated pages are taken to be English. If English already has its own folder, GitCMS can't tell which language they are: it uses the first language found as the default, so confirm it in **Configure** → **Languages**.
