---
title: Localization (i18n)
description: Configure multilingual content in GitCMS with locale-aware collection paths, default locale behavior, and per-locale overrides.
---

GitCMS supports locale-aware content workflows for multilingual sites.

You can:

- define site locales (for example `en`, `fr`, `de`)
- choose a default locale
- control whether the default locale is prefixed in paths
- configure per-collection locale path overrides

## Site-level i18n settings

In **Settings → General**, enable i18n and configure:

| Setting | Purpose |
|---------|---------|
| **Locales** | Allowed locale codes for the site |
| **Default locale** | Fallback locale when none is selected |
| **Default locale path** | Whether default locale should be prefixed in paths |

![Global i18n settings](/images/docs/screenshots/i18n-settings.webp)

## Default locale path behavior

Assume collection path is `/posts/`, default locale is `en`, and secondary locale is `fr`.

| Option | `en` path | `fr` path |
|--------|-----------|-----------|
| Default locale path **off** | `/posts/hello-world` | `/posts/fr/hello-world` |
| Default locale path **on** | `/posts/en/hello-world` | `/posts/fr/hello-world` |

## Collection-level i18n

In each collection, enable i18n when that collection should be localized.

- Strategy is path-based (`path`).
- You can add `locale_paths` overrides for framework-specific folder structures.

Example:

```yaml
i18n:
  enabled: true
  locales:
    - en
    - fr
  default_locale: en
  prefix_default_locale: false
collections:
  - name: docs
    git_path: /content/docs/
    i18n:
      enabled: true
      strategy: path
      locale_paths:
        fr: /content/fr/docs/
```

## Editor behavior

- Web app locale switcher keeps you in the same context (entry, history panel, or collection) while switching locale.
- New-entry drafts are locale-scoped, so drafts for `en` and `fr` do not collide.
- Production link and collection listing respect the selected locale context.

![Locale switcher in the editor](/images/docs/screenshots/locale-switcher.webp)

## MCP and AI behavior

GitCMS MCP tools are locale-aware.

For multilingual workflows, explicitly mention target locale in your prompt (for example: "use locale `fr`"). This helps AI read and write the intended locale path.

## Detection during onboarding

Setup, in the web app and the CLI, sets up i18n for you.

**Your framework's language config comes first.** When a site declares its languages, those are the site's languages and its default, and only folders named after them are treated as translations. GitCMS reads:

- Hugo `languages` in `hugo` or `config` files, including `config/_default/languages.*`
- Astro `i18n`, or Starlight `locales`
- Next.js `i18n` in `next.config` or `next-i18next.config`
- Nuxt `i18n`

**Otherwise GitCMS reads the folders.** Only real language codes, such as `fr` or `pt-br`, count.

- **All language folders.** When a collection holds two or more language folders and nothing else, such as `content/en/` and `content/fr/`, each is a language, even if the page names are translated.
- **Beside other content.** A language folder next to other pages or folders counts only when its pages mirror them: at least half exist at the same path among the untranslated pages, or it shares at least half the pages of the smaller of the two with another language folder.

So a folder like `it/` holding IT service pages beside your other posts stays an ordinary folder.

Untranslated pages are taken to be English. If English already has its own folder, GitCMS can't tell which language they are: it uses the first language found as the default, so check **Default locale** in Settings.
