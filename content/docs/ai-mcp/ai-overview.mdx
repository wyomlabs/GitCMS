GitCMS connects AI assistants to your content workflow through the [Model Context Protocol (MCP)](https://modelcontextprotocol.io/).

Today, GitCMS documents MCP setup for **ChatGPT**, **Claude**, coding agents (**Claude Code**, **Codex**, **Cursor**), and static-token clients. In ChatGPT and Claude, GitCMS can open the editor inside the chat, work with your site configuration, and edit content using the publishing mode your site already uses.

You do not need to speak in Git or CMS implementation terms to use it well. Prompts like "edit this blog post", "tighten this page", or "rewrite this live URL" are valid starting points.

The useful part is not just “AI writes content.” GitCMS gives the model:

- your site scope
- your collections, site data, and their fields
- your editorial workflow
- your [`CONTENT.md`](/docs/ai-mcp/content-instructions) writing instructions
- a visual editor and review path instead of copy-paste busywork

## Before you start

Before using GitCMS with AI, make sure:

- your repository is connected in GitCMS
- `.gitcms` has been initialized
- your site uses **GitCMS configuration v1.4**. If it still uses v1.2 or earlier, open the site in GitCMS and ask a workspace owner or admin to select **Upgrade configuration**. MCP will give your assistant a link to the right site if an upgrade is needed.
- the site is **licensed** because MCP is not available in preview mode
- your `CONTENT.md` file is in reasonable shape if you want stronger brand-voice guidance

Useful links:

- [CLI Onboarding](/docs/getting-started/cli-onboarding) if `.gitcms` is not set up yet
- [Licensing & Preview](/docs/getting-started/licensing) for MCP access rules
- [CONTENT.md](/docs/ai-mcp/content-instructions) for site-wide writing instructions

## How GitCMS MCP works today

GitCMS follows the site's publishing mode instead of forcing every AI edit through the same workflow.

If your site uses **Review before publish**, MCP is task-first: create or resume a content task, draft in its folder, and submit it for review.

If your site uses **Direct publish**, MCP does not create content tasks. Writes and precise edits commit directly to the site's publishing branch, just like saves from the GitCMS web editor.

In the fullscreen editor, Ask AI uses a precise Git-backed edit. GitCMS shows the committed change as an inline diff. **Keep** leaves that commit in place; **Undo** creates a new commit that restores the previous content.

When GitCMS loads a site, the host may show a small context card confirming the site and publishing mode. The full editor is reserved for `write`; later `edit` calls stay conversational and are reflected in the already-open editor instead of opening another UI.

## How the model sees your site

The model gets one filesystem per connection, and it works with your site the way a coding agent works with files. It sees folders shaped by your GitCMS configuration, not your whole repository. Every site lives under `/sites/`:

```text
/sites/example.com/GITCMS.md                        a generated guide to the site (read-only)
/sites/example.com/CONTENT.md                       your editorial rules
/sites/example.com/skills/seo-refresh/SKILL.md      team skills from .gitcms/sites/<site>/skills/ (read-only, when defined)
/sites/example.com/content/posts/hello-world.mdx    an entry: frontmatter, then the body
/sites/example.com/content/docs/fr/setup.md         translated collections start with the locale
/sites/example.com/content/posts/.schema.json       the collection's fields (read-only)
/sites/example.com/content/navigation.json          site data, shown as JSON
/sites/example.com/tasks/12-launch-post/TASK.md     a content task's brief (Review before publish)
/sites/example.com/tasks/12-launch-post/content/…   the task's draft of the same files
```

- **The site folder** is named after the website's hostname, or the site's slug when it has no website URL. If two sites would share a name, GitCMS adds the workspace to tell them apart. Paths replace the site and task identifiers earlier versions asked for: a site is its folder, a content task is its number (`12-launch-post`; the slug after the number is only a label).
- **Entries** are the real Markdown files. GitCMS still checks their fields before saving and fills in managed fields like created and updated dates.
- **Site data** such as navigation, footers, or theme settings shows as JSON. GitCMS writes changed values back into the original JSON, YAML, or TOML file and keeps its comments and formatting. Keys outside your configured site data never appear.
- **Field definitions** show as JSON Schema files. They can't be changed through MCP; edit them in **Configure**.
- **`CONTENT.md`** is part of the site folder, and `open_site` returns it with the guide. Site managers can ask the model to update it; changes apply site-wide right away, outside any content task. Other editors can still read the rules.
- **Team skills (`skills/`)** are optional, repository-backed playbooks stored in `.gitcms/sites/<site_key>/skills/<skill-name>/SKILL.md` (with YAML frontmatter `name` and `description`, plus any sibling reference files). When present, GitCMS lists them in `GITCMS.md` and exposes them read-only under `/sites/<site>/skills/` so agents read the matching `SKILL.md` before starting.
- **Tasks** exist only on sites that use Review before publish. Inside a task's `content/` folder the model reads and writes the task's draft; the same path under the site's `content/` folder is the live site. Direct publish sites have no `tasks/` folder.

## The six tools

The model gets six tools. You do not need to call them yourself, but it helps to know what each one does:

| Tool | What it does |
| --- | --- |
| `open_site` | Loads a site's guide: its files, publishing mode, search sources, team skills, and your writing instructions |
| `bash` | Reads the workspace with a read-only shell: `ls`, `cat`, `grep`, `find`, `jq`, pipes, and read-only `gitcms` subcommands |
| `read` | Opens one file in full, with the revision that `write` needs to replace it |
| `write` | Creates a file or replaces its full content; a replacement needs the revision returned by `read`, so a stale draft cannot silently overwrite newer work |
| `edit` | Makes one or more precise `oldText` → `newText` edits to an existing file, including frontmatter and site data |
| `gitcms` | Runs GitCMS's own commands: content tasks, history, checks, the sitemap, media, search data, and moving or copying entries |

### Reading with bash

`bash` is how the model explores. It can list collections, search across entries, and pull values out of site data in one step:

```bash
ls /sites
grep -rl "pricing" /sites/example.com/content/posts
jq . /sites/example.com/content/navigation.json
```

It has no network access, and nothing you change in it is saved; edits go through `write` and `edit`. A single command reads one site, searches a site's `content/` folder whole from a cached snapshot (skipping individual files over 1 MiB with a notice, and falling back to folder listings on sites over 16 MiB), loads at most 20 non-content files, lists at most 50 folders, and runs for at most 20 seconds. When GitCMS has to stop a command (a limit, a second site, a path it won't serve), the output ends with a `[Stopped by GitCMS: …]` line saying why, and what was printed before it is kept.

### Changing files with write and edit

`edit` is the default for changing an existing entry or site data. `write` creates a file or replaces most of one. Before it creates an entry, the model reads the collection's `.schema.json`. On Review before publish sites, both write inside a task's `content/` folder; a write outside a task is rejected. On Direct publish sites, every write commits to the publishing branch.

### Tasks, history, checks, and search with gitcms

`gitcms` takes the text you would type after the command, such as `task submit /sites/example.com/tasks/12-launch-post/`. Some subcommands only read, and those also run inside `bash`, so their output can be piped to `grep` or `jq`:

- `task list`, `task show`, `task diff`: find content tasks with their updated/published dates (`--window 30d|90d|all`), see a task's stage and brief, and see what its draft changes
- `history`: see when a site, collection, or entry changed (`--since`, `--limit`), or list each entry's last-updated date across a collection with `--last-updated`
- `check`: look for search, sharing, alt-text, and broken-link problems on an entry (inside a task, on the draft preview too) — used for new entries, metadata/link/image edits, renames/deletes, and SEO refreshes
- `sitemap`: list the pages on the live website, each with its entry when it has one
- `media list`, `media url`: list images in a media library and preview a media reference
- `search site`, `search pages`, `search page`, `search opportunities`, and `index`: [search data](#search-data)

Subcommands that change the site run only through the `gitcms` tool, never inside `bash`:

- `task new`: start a content task and print its folder
- `task submit`: send the draft for review
- `task publish`: publish a reviewed task, if you are allowed to publish on this site
- `entry mv`, `entry cp`: rename, move, or copy an entry in one commit

An unknown subcommand or option is a usage error with help, never a partial change. `gitcms --help` lists everything.

Review-mode prompts that say “brainstorm first, then create a content task, then draft” work well when review is required. Direct sites can simply ask GitCMS to edit the relevant page or post.

You still do not need to name tools directly. The better pattern is to express intent in plain language and let GitCMS load the right context.

### Search data

When the site has Google Search Console or Bing Webmaster Tools connected, the model can ground changes in the searches people actually make. It starts from `gitcms search opportunities --kind all` (striking-distance searches, low click-through, declining pages, cannibalization, uncovered queries, and questions in one call) or `gitcms search pages` to compare a collection's entries, checks one entry with `gitcms search page` and `gitcms history`, and runs `gitcms index` on an entry that gets no searches to see whether its page is indexed.

Each command reads one source, chosen with `--source google` or `--source bing`. Google is the default when it is connected. The two sources measure different search engines, so GitCMS never combines their numbers. Bing data is weekly and has no country or device breakdown, and its index status only says whether Bing crawled a page. A source that isn't connected for the site answers with how to connect it. A workspace owner or admin connects them in **Workspace settings → Integrations**.

## Recommended workflow

Here is the workflow we recommend in docs and examples:

1. **Brainstorm**
   Ask the model to help with topic angles, outlines, and audience fit before it creates anything.
2. **Create a content task**
   Turn the chosen idea into a task with notes, references, and desired outcome.
3. **Draft the first version**
   Be explicit about collection, entry path, locale, and frontmatter values you care about.
4. **Revise**
   Ask for structural rewrites, tighter intros, stronger CTAs, or better examples.
5. **Submit for review**
   Use the same review path as the rest of your team.

For example:

```text
Help me brainstorm three post ideas for our developer docs audience.
Do not create content yet.
```

```text
Create a content task for the strongest idea.
Title it "Migrating from WordPress to a markdown-based docs workflow"
and include notes about target audience, angle, and CTA.
```

```text
Now draft the first version for that content task in the posts collection.
Keep the tone practical and leave it ready for review.
```

```text
I want to edit this blog post:
https://gitcms.dev/blog/content-is-just-code

Please read it first, then rewrite the introduction to be sharper and less repetitive.
```

See [Task-First AI Workflows](/docs/ai-mcp/task-first-workflows) for more complete prompt patterns.

## What AI is good at in GitCMS

GitCMS MCP is particularly useful for:

- turning brainstormed ideas into first drafts
- revising existing docs, blog posts, and changelogs
- adding or updating frontmatter with valid field values
- updating site data such as menus, footers, and homepage sections
- repetitive editorial tasks across many entries
- locale-aware content work when you specify the target locale
- reviewable fullscreen edit suggestions during rewrite sessions

## CONTENT.md matters

If you want better output, keep [`CONTENT.md`](/docs/ai-mcp/content-instructions) current.

That file gives the model reusable guidance like:

- who you write for
- your brand voice
- what to avoid
- preferred structure
- terminology to keep consistent

Think of `CONTENT.md` as the persistent editorial brief the model can reuse across many content tasks.

You do not need to tell ChatGPT or Claude to "use CONTENT.md". GitCMS loads those instructions as part of site context during writing flows.

## Safety and limits

GitCMS MCP follows the publishing behavior you configured for the site.

- **Review before publish** keeps AI work in the editorial workflow until review and publishing
- **Direct publish** commits AI writes directly to the publishing branch, so your deployment pipeline may make the change live immediately
- schema validation still applies
- your repository remains the source of truth
- precise edits fail instead of overwriting content when the expected text or file revision no longer matches
- `bash` is read-only and has no network access, so exploring a site can't change it
- publishing with `task publish` only works where you are allowed to publish, and never skips a missing approval

Choose Review before publish when you want human approval before AI changes can ship.
