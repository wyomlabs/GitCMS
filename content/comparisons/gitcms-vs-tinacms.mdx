TinaCMS is the most technically ambitious Git-based CMS on the market. It is open source (Apache 2.0), now on version 3, and offers in-context visual editing, a GraphQL data layer over your Git content, schema-as-code in TypeScript, and a backend you either use as a service (TinaCloud) or self-host. If you want a Git CMS with the feature depth of a headless CMS, Tina is a serious option.

GitCMS is less ambitious about the data layer by design. It keeps content as plain files, gives clients and marketers a visual editor, and runs review and publishing for people and AI agents on top of Git. No GraphQL. No CMS package in your codebase. The content is the files.

The deeper difference is who each tool is for. Tina calls itself a visual editor for developers: you integrate it into your app and build the editing experience. GitCMS is for the people and agents who run the site after launch, connected to a repo that already exists.

## What changed in 2026

Git-based CMSs started as tools for developers who already preferred static sites and Markdown. That audience still exists. But a much larger group now arrives at the same architecture by a different road: they had Claude Code, Codex, or Cursor build the site, and the site naturally lives in Git.

That group doesn't mainly need a nicer way for developers to edit Markdown. They need **Day Two**: a way for clients and marketers to run the site without Git, and a way to review what AI agents change before it goes live. TinaCMS is a powerful Git-backed CMS you integrate into your codebase, with a GraphQL layer and live preview. GitCMS is built around that Day Two workflow: a hosted admin you connect to an existing GitHub repo, review before publish, and bring-your-own agents through MCP.

## Where the approaches diverge

Both GitCMS and TinaCMS store content in a Git repo. That shared foundation is real, and it is why both are better than database-backed CMSs for text-heavy content sites.

But what each tool builds on top of that foundation is different.

### TinaCMS adds a data layer

TinaCMS introduces a **GraphQL data layer** between your content files and your application. Content is typed by schema definitions, indexed by a backend, and queried through GraphQL. TinaCloud runs that backend for you. Self-hosting means running your own: an API function with an auth provider, a database adapter for indexing (MongoDB or Postgres, for example), and a Git provider.

That gives you structured queries and type safety over Markdown files. The cost is more infrastructure and more abstraction between you and your files, and the integration lives in your codebase.

### GitCMS stays closer to the files

GitCMS does not add a data layer. Your site reads its content files the way it already does. The editor writes them as files. There is nothing to install in the site's code: a coding agent runs `create-gitcms`, detects your collections, and writes the `.gitcms/` configuration. One repository can hold several websites, each configured separately.

This means GitCMS can't do some things Tina does. You don't get click-to-edit on your live site. You don't get GraphQL queries over your content. What you get is fewer moving parts and a direct relationship between the editor and the file.

## The editor question

TinaCMS's marquee feature is **contextual visual editing**: you edit content beside your rendered page and see changes in real time. This is powerful for layout-heavy pages where seeing the final result matters.

GitCMS gives you a **document-style visual editor**: slash commands, drag-and-drop blocks, tables, callouts, and frontmatter as typed form fields. Menus, footers, and team lists in JSON, YAML, or TOML files are edited as forms. It is built for writing, not page building.

Different editors for different jobs. If your content is primarily text, a writing-focused editor is more natural. If your content is layout-heavy, Tina's contextual editing has a real advantage.

## Review, clients, and agents

Tina's editorial workflow (branch-based drafts and review) is on its paid Team plan and up. GitCMS is built around review, because that's what clients and agents need:

- **Content board.** Content tasks move through Ideas, Draft, Review, and Published.
- **Reviews in the editor.** Inline comments, changes marked inline, approve or request changes.
- **Editors without GitHub accounts.** Invited editors sign in with Google and see only their site.
- **Preview deployments (beta)** and **Change Requests (beta)**, where clients pin feedback on the live site and it becomes a GitHub issue your coding agent can pick up.

On AI, Tina lists "AI features" as coming soon on its Team plan as of October 2026. GitCMS's MCP access is available now: ChatGPT, Claude, and other MCP clients read and edit entries and site data, draft inside content tasks, and submit for review. A person publishes, and you bring the agent you already use.

## Where TinaCMS is genuinely better

TinaCMS is the stronger choice when you need **a programmable, open-source Git CMS with visual editing**.

- **Contextual visual editing** directly beside the rendered site, for layout-heavy pages.
- **A GraphQL data layer** for programmatic content queries.
- **Schema-as-code** in TypeScript for complex content models.
- **Open source and self-hostable**, backend included, under Apache 2.0.
- **A free tier** that covers small projects with two users.

Tina is solving a harder problem and solving it well. For teams that need that depth, it earns its complexity.

## Where GitCMS is better

GitCMS is better when **the site already exists and the people running it aren't developers**.

Most content-heavy sites (docs, blog posts, changelogs, marketing pages) don't need a GraphQL layer. They need a good place to write, review before publishing, and a system that stays out of the codebase.

- **No integration work.** A coding agent runs `create-gitcms`; the site's code doesn't change.
- **Review as the default**, not an upsell: content board, reviews in the editor, preview deployments (beta).
- **Agents available today.** ChatGPT, Claude, and other MCP clients draft for review.
- **Client-friendly access.** Google sign-in, per-site access, and Change Requests (beta) on the live site.

If you don't need Tina's depth, you're carrying complexity that doesn't serve you.

## Decision by use case

**Git CMS with visual editing and a GraphQL data layer:** TinaCMS is the better fit.

**Open-source CMS you want to self-host end to end:** TinaCMS is the better fit.

**Complex content models with deep schema customization:** TinaCMS is the better fit.

**Agency handing a Claude Code or Astro site to a client:** GitCMS is the better fit.

**AI agents drafting website changes with human review before publishing:** GitCMS is the better fit.

**Existing site where you'd rather not add a CMS integration to the code:** GitCMS is the better fit.
