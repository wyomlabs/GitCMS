Pages CMS has an honest pitch: "the simplest CMS you'll ever need." You manage content and media right in your GitHub repo, with no database and nothing in your site beyond a `.pages.yml` config file. It is free, MIT-licensed, works with Astro, Hugo, Jekyll, Eleventy, Next.js, and more, and you can use the hosted app or self-host it. For personal sites and simple projects, it is a genuinely good answer.

GitCMS solves a bigger problem. It sits on the same foundation and adds what a site needs once clients, marketers, and AI agents are changing it: a content board, review before publish, reviews in the editor, and MCP access for agents. That extra surface area has a cost, in price and in concepts, and for some sites it's unnecessary. For others, it's what turns "Markdown files in a repo" into a site a team can run.

## What changed in 2026

Git-based CMSs started as tools for developers who already preferred static sites and Markdown. That audience still exists. But a much larger group now arrives at the same architecture by a different road: they had Claude Code, Codex, or Cursor build the site, and the site naturally lives in Git.

That group doesn't mainly need a nicer way for developers to edit Markdown. They need **Day Two**: a way for clients and marketers to run the site without Git, and a way to review what AI agents change before it goes live. Pages CMS is a free, lightweight editor for GitHub repositories. GitCMS is built around that Day Two workflow: a hosted admin you connect to an existing repo, review before publish, and bring-your-own agents through MCP.

## Where the approaches diverge

Both Pages CMS and GitCMS work directly with files in a GitHub repo. No content database, no sync layer. That shared foundation is the right one.

The difference is how much workflow sits on top.

### Pages CMS: keep it minimal

Pages CMS gives you configurable content types, a rich-text editor, a drag-and-drop media manager, and search, all mapped to files in the repo. You can invite collaborators by email, and they don't need a GitHub account. Saves commit straight to the repository. There are no drafts or review step; its "coming soon" list covers scheduling, granular permissions, S3 and R2 media storage, and inline comments.

This is the right model when the workflow is simple: one person edits, the change goes live.

### GitCMS: add structure where it helps

GitCMS adds the layers that matter once more than one person, or an agent, changes the site:

- **Content board.** Content tasks move through Ideas, Draft, Review, and Published. With review before publish, drafts stay off the live site until approved; direct publish is there for sites that don't need it.
- **Reviews in the editor.** Inline comments beside the text, changes marked inline, approve or request changes.
- **A document-style visual editor** with slash commands, drag-and-drop blocks, tables, and callouts, plus forms for site data like menus and footers.
- **Roles and per-site access**, with Google sign-in for invited editors.
- **Setup by a coding agent.** `create-gitcms` detects collections and writes the config, including for repos with several sites.

That structure is unnecessary for a personal blog. It's essential for an agency handing a site to a client, or a startup publishing docs, blog, and changelog as a team.

## AI agents and the workflow gap

Coding agents work natively with Markdown files in a repository. That's true under both tools.

The difference is what happens after the edit. With Pages CMS, there's no draft state or review step to route an agent's change through. It's a commit.

GitCMS gives **content agents** a structured path. ChatGPT, Claude, and other MCP clients read and edit entries and site data, draft inside content tasks, and submit for review. A person publishes. Developers get two more tools for client work, both in beta: **preview deployments**, so reviewers see drafts on the real site, and **Change Requests**, where clients pin feedback on the live site and it becomes a GitHub issue your coding agent can pick up.

For solo projects, commit-and-publish works. For teams and clients, review keeps an agent's draft from going live unseen.

## Content as code

Both tools deliver the same content-as-code benefits:

- **`grep` works.** Search your entire content library with standard dev tools.
- **`git log` works.** Every content change has a commit, an author, a timestamp, and a diff.
- **`git blame` works.** Trace any sentence to the person or agent that wrote it.
- **Deploys are atomic.** Content and code ship together.

Content is files. The workflow is Git. Neither tool locks you in.

Pages CMS is free. Full stop. If your project has no budget and your workflow is simple, that's an advantage GitCMS can't match.

GitCMS is a paid hosted product. You're paying for the review workflow, the editor, and MCP access, not for content storage; both store content the same way. See pricing above.

## Where Pages CMS is genuinely better

Pages CMS is the stronger choice when **simplicity and zero cost are the priorities**.

- **Free and open source**, hosted or self-hosted.
- **Very little to learn.** Configure content types, edit, save.
- **No account for collaborators.** Email invites, no GitHub account needed.
- **A thin layer over GitHub**: one `.pages.yml` file and you're editing.

Its last release was 2.1.8 in June 2026, so expect a steady tool rather than a fast-moving one. For a personal site, portfolio, or small docs site, Pages CMS is not a compromise. Its simplicity is the feature.

## Where GitCMS is better

GitCMS is better when **the site needs a workflow, not just an editor**.

Once a client, a team, or an agent is involved, the questions change:

- Who reviewed this post before it went live?
- Where are the drafts that are in progress?
- Can an AI agent draft content without it going live immediately?
- How does a client tell the developer that the hero image is wrong?

These are workflow questions, not storage questions. Pages CMS stores content the way GitCMS does. GitCMS adds the content board, reviews, agent access, and Change Requests (alpha) that answer them.

<Tradeoffs>
  <p>Choosing GitCMS over Pages CMS is a real tradeoff:</p>
  <ul>
    <li>Pages CMS is free. GitCMS is a paid product. For zero-budget projects, Pages CMS has the advantage.</li>
    <li>Pages CMS is simpler: less to learn, less to configure, less that can go wrong.</li>
    <li>If your workflow is "edit and publish" with no review needed, Pages CMS does exactly that.</li>
    <li>Pages CMS is open source and self-hostable. GitCMS is a hosted product from a company.</li>
  </ul>
  <p>For agencies, teams, and anyone letting AI agents draft changes, these tradeoffs are usually worth it: review before publish, client access, and agents that propose instead of publish.</p>
</Tradeoffs>

## Decision by use case

**Personal site, portfolio, or simple documentation:** Pages CMS is a great choice.

**Zero budget, simple editing needs:** Pages CMS is the right answer.

**One editor, no review workflow needed:** Pages CMS is plenty.

**Agency handing a Claude Code or Astro site to a client:** GitCMS is the better fit.

**AI agents drafting website changes with human review before publishing:** GitCMS is the better fit.

**Startup publishing docs, blog, and changelog as a team:** GitCMS is the better fit.
