Payload is one of the most exciting CMSs to emerge in recent years. It is TypeScript-native, installs into a Next.js app, MIT-licensed, and genuinely developer-friendly. If you want a headless CMS that feels modern and lives close to your code, Payload is a strong choice.

But Payload is still a **database-backed application CMS**. It runs a server, talks to a database (MongoDB, PostgreSQL, or SQLite), and delivers content through an API. That is the right architecture when your content model is complex and relational.

For content-heavy sites where the content is fundamentally text — docs, blogs, changelogs, marketing pages — GitCMS asks: why run a content server when the content could just be Markdown files in the repo?

## What changed in 2026

Payload's own story changed. Figma acquired Payload in June 2025, and the team says Payload remains open source and self-hostable. New Payload Cloud projects are paused, so new projects host Payload themselves, anywhere a Next.js app runs. In October 2026, Figma started bringing Payload into Figma Make, so prompt-built sites there can come with a CMS and admin panel that Figma hosts.

Meanwhile, more and more websites are built and maintained by coding agents working directly in a repository. Content in Payload is a second source of truth: it lives in a database, your Git history doesn't record it, and every page has to query it. Payload's MCP plugin lets agents reach it, but an agent building or changing a page still works across code and a database.

For sites whose content is mostly pages and posts, keeping content as files in the repo is simpler. The agent sees everything, every change is a commit, and GitCMS gives clients and marketers the editor and review workflow the headless dashboard used to provide. That's Day Two: running the site after it ships.

## Why this choice matters more than it looks

Payload runs inside your Next.js app, which is a more elegant architecture than most headless CMSs. But it still needs a database and a server runtime. That means:

- **Infrastructure to maintain** — even embedded in Next.js, you need a database running, backed up, and scaled.
- **Build-time queries** — static pages still fetch content from the database at build time. Every page is a database query.
- **Runtime dependency** — the CMS and the site share a runtime. If the database is down, the admin panel and potentially the site are affected.
- **Database migrations** — content model changes on SQL databases require migrations, which can be tricky in production.

With Markdown files in the repo, content is already on disk. No database. No runtime dependency. No migrations. Pre-rendering reads files locally — pure CPU, no I/O wait.

For text-heavy content sites, the database layer is often solving a problem they don't have.

## Framework fit

Payload is built for Next.js. If your site is Next.js and you also need app features — users, uploads, access control — that is a genuine advantage: one codebase, one deploy. Other frontends can use Payload as a headless API, but then you run a separate Next.js app just for the CMS.

Most content sites built with coding agents aren't only Next.js, though. GitCMS works with Astro, Next.js, Hugo, Eleventy, Docusaurus, Nuxt, SvelteKit, and similar frameworks, reads the Markdown and data files they already use, and leaves hosting wherever the site already deploys. One repository can even hold several separately configured sites.

## Content as code

When content lives in Markdown files inside a Git repository:

- **`grep` works.** Search your entire content library with standard dev tools.
- **`git log` works.** Every content change has a commit, an author, a timestamp, and a diff.
- **`git blame` works.** Trace any sentence to the person or agent that wrote it.
- **Code review works.** Content changes and code changes live in the same history.
- **Deploys are atomic.** Content and code ship together. No database state to sync.

Payload's TypeScript-native approach is a genuine improvement over older CMSs. But the content still lives in a database. You cannot grep it or review it alongside code changes. Payload's admin panel is the primary interface for content — not Git.

## AI agents and Markdown

Coding agents — Claude Code, Codex, Cursor — work natively with files in a repository. When your content is Markdown:

- Agents can **read, write, search, and diff** content with zero special tooling
- No database queries, no API calls, no admin panel to navigate
- Content is **inspectable** — an agent can open the file and understand the structure immediately
- Every agent edit lands in a Git commit

Payload has its own answer: an open-source MCP plugin that exposes find, create, update, and delete operations per collection, with each operation allowed or blocked in config. For an app that already runs Payload, that is a clean way to give agents access.

GitCMS takes the other route: content stays in files, and the **MCP app** gives ChatGPT, Claude, and other MCP clients structured access to it. Agents read and edit entries and site data, draft inside a content task, and submit for review. People approve and publish. Bring your own agent; GitCMS sells no AI credits.

## Where Payload is genuinely better

Payload is the stronger choice when you need a **TypeScript-native application CMS**.

If your team needs:

- A CMS that lives inside your Next.js app, deployed with it
- Rich, relational content models defined in TypeScript
- A polished admin panel with field-level access control
- Upload management, authentication, and content workflows built in
- An open-source CMS with a modern TypeScript stack you can extend deeply
- Content as a backend for application features, not just a website

Then Payload is excellent. It is one of the best developer experiences in the CMS space, and its Next.js embedding model is genuinely innovative.

## Where GitCMS is better

GitCMS is better when the content does not need an application CMS.

If the real job is publishing docs, blog posts, changelogs, and marketing pages — Payload's powerful admin panel, database, and API are all infrastructure for a problem that Markdown files already solve.

GitCMS removes the entire application layer:

- No database to host or migrate
- No admin panel server to maintain
- No API to secure or cache
- Content ships with the code in the same deploy

Editors still get a real admin: a visual document editor, site data as forms, reviews beside the text, and Google sign-in instead of a user table you maintain.

<Tradeoffs>
  <p>Choosing Markdown-in-Git over Payload is a real tradeoff:</p>
  <ul>
    <li>Payload's content modeling is richer — relational data, field validation, conditional logic. Frontmatter is simpler.</li>
    <li>Payload's admin panel is polished and customizable in code. GitCMS's editor is opinionated.</li>
    <li>Payload is open source and runs on your infrastructure. GitCMS's admin is a hosted service, even though your content never leaves your repo.</li>
    <li>If your project needs both content management and application features (auth, uploads, access control), Payload handles it in one system.</li>
  </ul>
  <p>For text-heavy content sites that are fundamentally read-only for end users, these tradeoffs are usually worth it. You get simpler architecture, faster builds, zero database overhead, full portability, and a workflow that works equally well for humans and AI agents.</p>
</Tradeoffs>

## Decision by use case

**TypeScript-native application CMS embedded in Next.js:** Payload is the better fit.

**Docs, blog, changelog, and marketing pages in one repo:** GitCMS is the better fit.

**Relational content models with admin panel and access control:** Payload is the better fit.

**Astro, Hugo, or another non-Next.js site whose clients need to edit content:** GitCMS is the better fit.

**CMS that also handles auth, uploads, and application features:** Payload is the better fit.

**Startup or small team that wants AI agents and humans collaborating in Git:** GitCMS is the better fit.
