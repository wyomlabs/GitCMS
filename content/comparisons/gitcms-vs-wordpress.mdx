WordPress is the most successful CMS ever built. [W3Techs](https://w3techs.com/technologies/details/cm-wordpress) counts it on 39.5% of all websites as of October 2026, with over 77,000 free plugins in its directory and a hosting and agency market around it. If you are reading this, you already know what WordPress is.

So the question is not whether WordPress is proven. It is whether you still need it in 2026, when an agent can build the site in code and the only thing missing is an admin.

For many content-heavy sites (marketing pages, blogs, docs, changelogs) WordPress means running a PHP application, a MySQL database, a plugin stack, and a security surface that needs ongoing maintenance. All to serve content that could live as Markdown files in a Git repository.

## What changed in 2026

For two decades, choosing WordPress made sense for one reason: building a custom website in code was slow and expensive, and WordPress gave non-developers a way to run the site.

That trade has flipped. Coding agents like Claude Code, Codex, and Cursor now build custom sites in hours, and designers, growth teams, and agencies iterate on pages directly in code. The result is faster, fully owned, and keeps improving because an agent can keep working on it. WordPress's share of the web is shrinking too: [W3Techs](https://w3techs.com/technologies/history_overview/content_management/all/y) measured it at 43.0% of all websites on 1 January 2026 and 39.5% on 28 October 2026.

What a code-first site doesn't come with is **the admin**: a safe place for clients and marketers to change copy, publish posts, update the menu, and review what agents changed. That's Day Two, and for most agencies it's the main thing they still need WordPress for. GitCMS is the CMS for code-first and AI-built websites. It gives your team, your clients, and AI agents one safe place to edit, review, and publish website changes, while everything stays in your site's repository.

## Why this choice matters more than it looks

WordPress is a dynamic application. Every uncached page request executes PHP, queries MySQL, and assembles HTML at runtime. That means:

- **Server infrastructure.** WordPress needs PHP hosting, a MySQL database, and usually a caching layer to perform well.
- **A runtime to keep patched.** WordPress core, every plugin, every theme, and the PHP runtime underneath them all need updates.
- **Plugin dependency.** Most WordPress sites rely on plugins for SEO, caching, security, backups, and forms. Each is a compatibility and security decision.
- **Database-bound content.** Posts live in MySQL as block markup. Getting them out means the WordPress XML export or a database dump, then conversion.

That runtime is a real exposure, not a theoretical one. On 21 October 2026, the PHP project [shipped PHP 8.5.12, 8.4.27, 8.3.36, and 8.2.35](https://www.php.net/archive/2026.php#2026-10-21-5) to fix two critical remote code execution bugs, CVE-2026-109618 and CVE-2026-109619, known as PHP2Shell. They sit in PHP itself, so a WordPress dashboard can report "everything is up to date" while the server is still vulnerable. Well-run hosts patched quickly. But every WordPress site depends on someone doing that. If you run one, [here's what to check](/blog/php2shell-wordpress/).

A prebuilt Astro or Next.js site served from Vercel, Netlify, or Cloudflare has no PHP runtime or site database to patch. For content that's read-only for visitors, WordPress is a dynamic application solving a mostly static problem.

## Content as code

When content lives in Markdown files inside a Git repository:

- **`grep` works.** Search your entire content library from the terminal.
- **`git log` works.** Every content change has a commit, an author, a timestamp, and a diff.
- **`git blame` works.** Trace any sentence to the person or agent that wrote it.
- **Review works.** With review before publish, edits wait as a draft until someone approves them.
- **Deploys are atomic.** Content and code ship together. No database state to sync.

WordPress keeps revisions for each post, and WordPress 7.0 added a visual view of them. But content and code still live in separate systems: your theme is in Git (if you're lucky), and your posts are in a database your developers rarely see.

## AI agents and WordPress

WordPress is moving here too. WordPress 7.0 added an AI Client and Connectors for OpenAI, Anthropic, and Google, plus a client-side Abilities API. In October 2026 the WordPress AI team put the official MCP Adapter plugin in the directory, so MCP clients like Claude can call the abilities a site exposes. It's a real step, and if you're staying on WordPress, it's worth installing.

The difference is what the agent touches. On WordPress, an agent works through abilities that each plugin chooses to expose, against a live database. On a code-first site:

- **Coding agents** (Claude Code, Codex, Cursor) read and edit the actual components and content files, with no API in between.
- **Content agents** (ChatGPT, Claude, and other MCP clients) connect to GitCMS, read and edit entries and site data, draft inside content tasks, and submit for review. A person publishes. GitCMS sells no AI credits; you bring the agent you already use.

Every agent edit lands as a Git commit, so you can see exactly what changed and undo it.

## The plugin and theme ecosystem matters less than it used to

WordPress's moat has always been its ecosystem. Need a feature? There is a plugin for it. Need a design? There is a theme for it.

In 2026 that moat is narrower for content sites. Agents like Claude Code, Codex, Cursor, Lovable, and Bolt turn "build me a marketing site with a pricing page and blog" into an Astro or Next.js project in an afternoon. No theme marketplace, no plugin compatibility matrix, no PHP. And the person who built it owns the code.

For agencies, that changes the handoff. The site stays code, and the admin your client expects comes from GitCMS:

- A **visual editor** for pages and posts, with frontmatter as form fields
- **Site data forms** for menus, footers, team lists, and theme settings, so clients don't need you to change a nav link
- **Google sign-in** for invited editors, so clients never need a GitHub account
- **Reviews in the editor**: inline comments, changes marked inline, approve or request changes
- **Multiple sites in one repository**, each configured separately

## Where WordPress is genuinely better

WordPress is still the right choice for a lot of websites. Choose it when the site is more than content:

- **E-commerce.** WooCommerce and its extensions are a complete store. GitCMS doesn't do commerce.
- **Memberships, logins, and gated content.** WordPress handles them with mature plugins.
- **Plugin-heavy sites.** If the site depends on forms, bookings, LMS, directories, or a dozen other plugins, rebuilding all of that in code isn't worth it.
- **Visual page building by editors.** The block editor and Site Editor let non-developers create layouts. GitCMS edits content, not layout.
- **Open source, with the biggest ecosystem.** You can run it anywhere, and more than 20 years of themes, tutorials, and agencies come with it.

If any of those describe your site, keep WordPress, and keep it patched.

## Where GitCMS is better

GitCMS is better when WordPress is **more runtime than the job needs**.

If the real job is publishing pages, posts, docs, and changelogs, and the site is (or could be) code, GitCMS gives you:

- Content as files in your repository, with every save a Git commit
- A visual editor and site data forms clients can use without training
- Review before publish, with reviews in the editor and preview deployments (beta)
- [Change Requests](/features/change-requests/) (beta): clients pin feedback on the live site, and you hand it to Claude Code, Codex, or Cursor
- AI agents that draft through the same review workflow as people

No PHP. No MySQL. No plugin updates.

## Decision by use case

**Online store, membership site, or a site built on plugins:** WordPress is the better fit.

**Agency rebuilding client sites in Astro or Next.js with Claude Code:** GitCMS is the better fit.

**Non-technical team that builds new page layouts itself every week:** WordPress is the better fit.

**Marketing site, blog, and docs where clients edit copy, menus, and posts:** GitCMS is the better fit.

**Team that wants AI agents drafting changes with review before publish:** GitCMS is the better fit.
