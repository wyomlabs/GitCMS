Drupal is a serious content management system. It runs government sites, universities, media organizations, and large enterprise web properties. It is open source, highly configurable, and battle-tested across two decades. In January 2026 it shipped Drupal CMS 2.0, with the Canvas visual page builder as the default editing experience and optional AI tools built in.

But Drupal is still a **PHP application backed by a database**, with a real learning curve and operational overhead. For teams publishing text-heavy content (marketing pages, blogs, docs, changelogs) the question is whether Drupal's power is worth the complexity.

GitCMS is the CMS for code-first and AI-built websites. It gives your team, your clients, and AI agents one safe place to edit, review, and publish website changes, while everything stays in your site's repository.

## What changed in 2026

For two decades, choosing Drupal made sense for one reason: building a custom website in code was slow and expensive, and Drupal gave non-developers a structured way to run the site.

That trade has flipped. Coding agents like Claude Code, Codex, and Cursor now build custom sites in hours, and designers, growth teams, and agencies iterate on pages directly in code. The result is faster, fully owned, and keeps improving because an agent can keep working on it.

What a code-first site doesn't come with is **the admin**: a safe place for editors to change copy, publish posts, and review what agents changed. That's Day Two, and for many teams it's the main thing they still need Drupal for. GitCMS gives a code-first site that admin, so you can keep the code and still hand the website to the people who run it.

## Why this choice matters more than it looks

Drupal runs a PHP application backed by a database (typically MySQL, MariaDB, or PostgreSQL). Every uncached page request executes PHP, queries the database, and assembles HTML. That means:

- **Significant infrastructure.** Drupal needs PHP hosting, a database, and usually a caching layer. Large deployments often have a dedicated platform team.
- **Upgrade cycles.** Core updates, module updates, security releases, and major-version upgrades are ongoing work. The [official schedule](https://www.drupal.org/about/core/policies/core-release-cycles/schedule) has Drupal 10 reaching end of life on 9 December 2026, the same week Drupal 12 is due, so every Drupal 10 site needs an upgrade project.
- **The PHP runtime too.** In October 2026 the PHP project shipped emergency releases for two critical remote code execution bugs. Every Drupal host had to patch PHP itself, separately from Drupal.
- **Learning curve.** Configuring content types, views, permissions, and workflows takes real expertise.
- **Database-bound content.** Content lives in Drupal's database schema. Getting it out means migration tooling or custom exports.

With Markdown files in the repo, content is already on disk. No CMS server, no database, no module stack. For text-heavy sites that are read-only for visitors, Drupal is enterprise infrastructure solving a problem that files handle natively.

## Content as code

When content lives in Markdown files inside a Git repository:

- **`grep` works.** Search your entire content library with standard dev tools.
- **`git log` works.** Every content change has a commit, an author, a timestamp, and a diff.
- **`git blame` works.** Trace any sentence to the person or agent that wrote it.
- **Review works.** With review before publish, edits wait as a draft until someone approves them.
- **Deploys are atomic.** Content and code ship together. No database state to sync.

Drupal has solid revisions and content moderation, but content and code live in separate systems. You can't diff a Drupal content change next to the code change it depends on, and moving content out of Drupal takes migration work.

## AI agents and markdown

Drupal is investing in AI. Drupal CMS 2.0 can generate pages from a prompt with Canvas components, includes an admin chatbot for tasks like creating content types and fields, and suggests image alt text. Contributed modules like MCP Server (in beta as of October 2026) expose Drupal to MCP clients.

GitCMS takes a different route. AI coding agents (Claude Code, Codex, Cursor) work natively with files in a repository:

- Agents can **read, write, search, and diff** content with no API in between
- Content is **inspectable**: an agent opens the file and understands the structure
- Every agent edit lands in a Git commit, reviewable by people before it ships

For content agents, GitCMS has an **MCP app**. ChatGPT, Claude, and other MCP clients read and edit entries and site data, draft inside content tasks, and submit for review. A person publishes. GitCMS sells no AI credits; you bring the agent you already use.

Drupal the software is free. Running it at scale is not. Managed Drupal hosting, agency retainers, and major-version upgrades are where the money goes. Self-hosting means your team manages servers, databases, caching, security releases, and Drupal updates.

## Where Drupal is genuinely better

Drupal is the stronger choice when you need **enterprise-grade content management at scale**.

If your organization needs:

- Complex content types with rich field configurations and relationships
- Granular role-based permissions and multi-step moderation workflows
- Many sites and languages managed from one platform
- Visual page building for editors, now with Canvas
- Compliance, accessibility, and audit trail requirements
- Integration with enterprise systems (LDAP, SSO, CRM, marketing automation)
- A 20-year ecosystem of modules, distributions, and agencies

Then Drupal is built for problems that GitCMS does not try to solve. Government sites, universities, and large media organizations choose Drupal for a reason.

## Where GitCMS is better

GitCMS is better when Drupal is **enterprise infrastructure for a non-enterprise problem**.

Many teams running Drupal today publish text content (marketing pages, blog posts, docs, changelogs) that doesn't need complex content types or a PHP application server. With a code-first site and GitCMS:

- No PHP, no CMS database, no caching layer, no module updates
- No major-version migration projects for the CMS
- Editors get a visual editor, site data forms, and reviews in the editor, and can sign in with Google
- Client feedback on the live site goes straight to your coding agent with [Change Requests](/features/change-requests/) (beta)
- Content ships with the code in the same deploy

If your Drupal 10 site needs an upgrade project anyway, it's a natural moment to ask whether it should be a code-first site instead.

## Decision by use case

**Enterprise content platform with complex permissions and many sites:** Drupal is the better fit.

**Marketing site, blog, docs, and changelog in one repo:** GitCMS is the better fit.

**Government, education, or large media organization with compliance requirements:** Drupal is the better fit.

**Team facing a Drupal 10 upgrade for what is mostly a content site:** GitCMS is worth a look.

**Multilingual content management at enterprise scale:** Drupal is the better fit.

**Startup or agency that wants AI agents and people working through one review workflow:** GitCMS is the better fit.
